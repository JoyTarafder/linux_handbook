Linux File System Hierarchy

🗂️
📌 Core Concept
In Linux, everything is a file — hardware, processes, network sockets. All files live in a single-rooted, inverted tree structure starting from / (root).
/ (root)
├──/rootSuperuser's home directory. Only root can access this.
├──/homeHome directories for all non-root users (e.g., /home/joy)
├──/binEssential user binaries: ls, cd, cp, mv, rm, cat, grep, etc.
├──/sbinSystem binaries for admin: iptables, reboot, fdisk, ifconfig, swapon
├──/etcAll configuration files: /etc/passwd, /etc/shadow, /etc/fstab, /etc/hosts
├──/devDevice files: /dev/sda (hard disk), /dev/tty1 (terminal), /dev/null
├──/varVariable data: /var/log (logs), /var/mail, /var/tmp, /var/lib
├──/tmpTemporary files — cleared on every reboot. World-writable.
├──/usrUser-installed software & libraries: /usr/bin, /usr/lib, /usr/local
├──/optOptional third-party software (e.g., Docker, custom tools)
├──/bootBoot loader files: GRUB, Linux kernel images (vmlinuz)
├──/mntTemporary mount point for file systems (manual mounts)
├──/mediaAuto-mounted removable media: USB drives, CD-ROMs
├──/procVirtual FS — kernel & process info: /proc/cpuinfo, /proc/meminfo
└──/sysVirtual FS — hardware/kernel interface (sysfs)

Group Management

👥
💡 What is a Group?
A group is a collection of user accounts. Admins use groups to manage permissions for multiple users at once. Instead of assigning permissions to each user individually, assign to a group — all members inherit that permission.
Group Commands
# ── CREATE & DELETE ──────────────────────────────
groupadd ibmgrp              # Create a new group
groupdel ibmgrp              # Delete a group

# ── INSPECT ──────────────────────────────────────
grep ibmgrp /etc/group       # Check group properties
ibmgrp:x:1001:ajay,vijay,sachin
grep ibmgrp /etc/gshadow     # Check group admin info

# ── MEMBERS ──────────────────────────────────────
gpasswd -a ajay ibmgrp       # Add single member to group
gpasswd -M rahul,virat,rohit ibmgrp # Add multiple members
gpasswd -d virat ibmgrp      # Remove member from group
gpasswd -A sachin ibmgrp     # Make user a group admin

# ── USING usermod ────────────────────────────────
usermod -g ibmgrp shub       # Set primary group
usermod -aG ibmgrp shub      # Add to secondary group (keep existing)

# ── CHECK USER GROUPS ────────────────────────────
groups shub                  # List groups for a user
id shub                      # Full UID/GID/groups info

Access Control List (ACL)

🛡️
💡 Why ACL?
Standard Linux permissions only support one owner and one group. ACL lets you grant specific permissions to any user or group on any file — without adding them to the file's group.
ACL Commands (getfacl / setfacl)
# ── CHECK ────────────────────────────────────────
getfacl /devops              # View all ACL permissions on a file/dir

# ── USER ACL ─────────────────────────────────────
setfacl -m u:shub:rwx /devops   # Grant shub read+write+execute
setfacl -m u:shub:r-- /devops   # Grant shub read-only
setfacl -x u:shub /devops        # Remove all ACL for shub

# ── GROUP ACL ────────────────────────────────────
setfacl -m g:shubgrp:rwx /devops # Grant group permissions
setfacl -x g:shubgrp /devops     # Remove group ACL

# ── RECURSIVE ────────────────────────────────────
setfacl -Rm u:shub:rwx /devops   # Apply ACL recursively

# ── REMOVE ALL ───────────────────────────────────
setfacl -b /devops               # Remove ALL ACL permissions

# ── DEFAULT ACL (for new files in a directory) ───
setfacl -d -m u:shub:rw /shared  # New files auto-inherit this ACL

GREP & Regular Expressions

🔍
📌 What is GREP?
GREP = Global Regular Expression Print. It searches file(s) for a pattern and prints matching lines. One of the most powerful and frequently used commands in Linux.
grep — Complete Reference
# ── BASIC SEARCH ─────────────────────────────────
grep root /etc/passwd          # Search 'root' in one file
grep root /etc/passwd /etc/group # Search in multiple files

# ── OPTIONS ──────────────────────────────────────
grep -i Root /etc/passwd       # Case-insensitive search
grep -r root /                 # Search recursively through all files
grep -v root /etc/passwd       # Invert — show lines WITHOUT 'root'
grep -c root /etc/passwd       # Count matching lines
grep -n root /etc/passwd       # Show line numbers with matches
grep -l root /etc/passwd /etc/shadow # Show filenames that MATCH
grep -L root /etc/passwd /etc/shadow # Show filenames that DON'T match
grep -w root /etc/passwd       # Match whole word only
grep -A 3 root /etc/passwd     # Show 3 lines AFTER match
grep -B 3 root /etc/passwd     # Show 3 lines BEFORE match
grep -C 3 root /etc/passwd     # Show 3 lines AROUND match

# ── ANCHORS (Regex) ──────────────────────────────
grep ^root /etc/passwd         # Lines STARTING with 'root'
grep bash$ /etc/passwd         # Lines ENDING with 'bash'
grep '^$' file.txt              # Match empty lines

# ── EXTENDED REGEX (egrep / grep -E) ─────────────
grep -E 'root|admin' /etc/passwd  # Match 'root' OR 'admin'
grep -E 'ro{2}t' /etc/passwd      # Match 'root' (2 o's)
grep -E '[0-9]+' /etc/passwd      # Match one or more digits

# ── REDIRECT OUTPUT ──────────────────────────────
grep root /etc/passwd > /mnt/find.txt # Save results to file
grep -r 'error' /var/log/ | less   # Pipe to pager

Sudo Command

🔑
📌 What is sudo?
sudo = "superuser do" — allows a permitted user to execute commands as root (or another user) without switching to the root account. Configuration lives in /etc/sudoers.
/etc/sudoers — Configuration
# ── ALWAYS edit sudoers with visudo (safe editor) ─
visudo                           # Opens /etc/sudoers safely

# ── SYNTAX ────────────────────────────────────────
# user  HOST=(run_as_user) command
root    ALL=(ALL) ALL             # Root can do anything
amir    ALL=(ALL) ALL             # Grant 'amir' full sudo
amir    ALL=(ALL) NOPASSWD: ALL   # sudo WITHOUT password prompt

# ── GROUPS (prefix with %) ────────────────────────
%punegrp  ALL=(ALL) ALL           # All members of punegrp get sudo
%sudo     ALL=(ALL) ALL           # Default sudo group (Ubuntu)
%wheel    ALL=(ALL) ALL           # Default sudo group (RHEL/CentOS)

# ── RESTRICT TO SPECIFIC COMMANDS ─────────────────
amir    ALL=(ALL) /usr/bin/systemctl  # Only allow systemctl
amir    ALL=(ALL) /usr/bin/apt        # Only allow apt

# ── WHEEL GROUP (RHEL/CentOS shortcut) ───────────
useradd shub
passwd shub
gpasswd -a shub wheel             # Add to wheel = instant sudo
# Or:
usermod -aG wheel shub

# ── VERIFY ────────────────────────────────────────
sudo -l                           # List your sudo permissions
sudo -l -U shub                  # Check another user's sudo perms
sudo whoami                       # Should output: root

Systemd & Service Management

⚙️
Understanding systemd

systemd is the modern init system and service manager for Linux, replacing the legacy SysVinit and Upstart init systems. It is the first process started by the kernel (PID 1) and is responsible for bootstrapping the entire userspace — bringing up services, mounting filesystems, managing devices, and handling user sessions.

NOTE
Why systemd replaced SysVinit: SysVinit started services sequentially using shell scripts, making boot slow and configuration fragile. systemd starts services in parallel using dependency graphs, offers built-in logging (journald), socket activation, cgroup-based process tracking, and declarative unit files — making it far more reliable for production servers.

systemd Unit Types

Unit Type Extension Purpose
service .service Manages daemons and processes (nginx, sshd, your app)
socket .socket Socket-based activation — starts service on incoming connection
timer .timer Cron replacement — schedules periodic or one-shot tasks
mount .mount Controls filesystem mount points (auto-generated from /etc/fstab)
target .target Groups units into boot stages (like runlevels: multi-user, graphical)
path .path Watches file/directory changes and triggers a service
slice .slice Manages cgroup resource limits for a group of processes

systemd Architecture Overview

CORE DAEMON
systemd (PID 1) — Reads unit files, builds dependency tree, starts/stops services, manages cgroups. All processes are tracked — no orphan zombies.
LOGGING
journald — Binary structured logging. Captures stdout/stderr from all services. Queried with journalctl. Replaces traditional syslog for most use cases.
CONTROL

Creating Custom Service Files

Custom .service files let you run any application as a managed systemd service — with auto-restart, logging, resource limits, and boot persistence. Service files live in /etc/systemd/system/.

Custom .service File Template — /etc/systemd/system/myapp.service 
# ── [Unit] — METADATA & DEPENDENCIES ────────────────────────
# Defines what this service IS and what it needs before starting

[Unit]
Description=MyApp Node.js Production Server           # Human-readable name shown in systemctl status
Documentation=https://myapp.example.com/docs           # Link to docs — helps team members understand the service
After=network.target postgresql.service                # Wait for network & database BEFORE starting this service
Wants=postgresql.service                               # Prefer postgresql to be running (soft dependency, won't fail)
Requires=redis.service                                 # HARD dependency — if redis fails, this service stops too

# ── [Service] — HOW TO RUN THE APPLICATION ──────────────────
# Core execution settings — user, working dir, env vars, restart policy

[Service]
Type=simple                                            # simple = process stays in foreground (default for most apps)
                                                       # Other types: forking, oneshot, notify, dbus, idle
User=nodeapp                                           # Run as non-root user — NEVER run production apps as root!
Group=nodeapp                                          # Group for file permission control
WorkingDirectory=/opt/myapp                            # cd to this directory before executing — where your code lives

# Environment variables — choose ONE method:
Environment=NODE_ENV=production                        # Inline env var — good for simple values
Environment=PORT=3000                                  # Each Environment= line adds one variable
EnvironmentFile=/opt/myapp/.env                        # Load from file — best for secrets (keep .env out of git!)

ExecStartPre=/usr/bin/npm run migrate                  # Run BEFORE starting — database migrations, health checks
ExecStart=/usr/bin/node /opt/myapp/server.js           # Main command — MUST use absolute paths, no shell expansion
ExecStartPost=/usr/bin/curl -s http://localhost:3000/health   # Run AFTER start — verify app is healthy
ExecStop=/bin/kill -SIGTERM $MAINPID                   # Graceful shutdown command (default is SIGTERM anyway)
ExecReload=/bin/kill -SIGHUP $MAINPID                  # Command for systemctl reload — hot config reload

# Restart policy — CRITICAL for production reliability:
Restart=on-failure                                     # Restart only on failure (non-zero exit). Options:
                                                       #   always      — restart no matter what (even clean exit)
                                                       #   on-failure  — restart on crash/error exit only (recommended)
                                                       #   on-abnormal — restart on signal/timeout/watchdog
                                                       #   no          — never restart (for oneshot tasks)
RestartSec=5                                           # Wait 5 seconds between restart attempts (avoid crash loops)
StartLimitBurst=5                                      # Max 5 restart attempts...
StartLimitIntervalSec=60                               # ...within 60 seconds, then give up (prevents infinite loops)

# Resource limits & security hardening:
LimitNOFILE=65535                                      # Max open file descriptors — increase for high-traffic servers
MemoryMax=512M                                         # Hard memory limit — OOM kill if exceeded (cgroup v2)
CPUQuota=80%                                           # Limit CPU usage to 80% of one core
ProtectSystem=full                                     # Make /usr, /boot, /etc read-only — security hardening
PrivateTmp=true                                        # Isolate /tmp — prevents tmp-based attacks between services
NoNewPrivileges=true                                   # Prevent privilege escalation — essential for security

StandardOutput=journal                                 # Send stdout to journald (viewable with journalctl)
StandardError=journal                                  # Send stderr to journald — centralized error logging
SyslogIdentifier=myapp                                 # Custom name in logs (default is service filename)

# ── [Install] — BOOT INTEGRATION ────────────────────────────
# Tells systemd HOW to enable this service for auto-start

[Install]
WantedBy=multi-user.target                             # Start when system reaches multi-user mode (standard servers)
                                                       # This is the equivalent of runlevel 3 in SysVinit
                                                       # Use graphical.target for desktop GUI environments

Process Management — Core Concepts

A process is a running instance of a program. Every process gets a unique PID (Process ID) and knows its parent via PPID (Parent Process ID). The very first process (systemd or init) has PID 1 and is the ancestor of all other processes.

Process States

State Code Meaning
Running R Actively executing on CPU or waiting in the run queue, ready to execute
Sleeping S Waiting for an event (I/O, signal, timer) — most processes are in this state
Stopped T Paused by a signal (e.g., Ctrl+Z) — can be resumed with fg or bg
Zombie Z Process finished but parent hasn't read its exit status — takes no resources but occupies a PID slot
Defunct Z Same as Zombie — shown as <defunct> in ps output. The parent must call wait() to reap it
Uninterruptible Sleep D Waiting on I/O (usually disk) — cannot be killed until I/O completes. Common in NFS hangs

Foreground vs Background Processes

FOREGROUND
Runs attached to the terminal. The shell waits for it to finish. You interact with it directly.
Example: vim file.txt — the terminal is occupied until you exit vim.
BACKGROUND
Runs detached from the terminal. The shell returns immediately. Add & at the end to launch in background.
Example: ./backup.sh & — script runs while you continue working. Use jobs, fg, bg to manage.

Process Lifecycle

LIFECYCLE FLOW
fork() → Parent creates a child process (copy of itself) → exec() → Child replaces itself with a new program → Process runs → exit() → Process terminates → Parent calls wait() → Kernel removes the process entry.

If the parent never calls wait(), the child becomes a Zombie. If the parent dies first, the child is orphaned and adopted by PID 1 (systemd), which automatically reaps it.

# The zombie is already dead — you can't kill it. Killing the parent
# makes systemd (PID 1) adopt and reap the zombie automatically.
kill -SIGCHLD <PPID>                      # Ask parent to reap its zombie children (works if parent is well-coded)

System Resource Monitoring 
# ── MEMORY MONITORING ────────────────────────────────────────
free -h                                    # Show memory usage in human-readable format (GB/MB)
# Sample output:
#               total    used    free    shared  buff/cache  available
# Mem:           16Gi    6.2Gi   1.8Gi   512Mi   8.0Gi       9.1Gi
# Swap:          4.0Gi   0.0Gi   4.0Gi
#
# KEY INSIGHT: "free" is NOT what's actually available!
#   total     = Total physical RAM installed
#   used      = RAM actively used by programs
#   free      = Completely unused RAM (Linux keeps this LOW — it uses RAM for cache!)
#   shared    = Memory used by tmpfs (shared memory)
#   buff/cache = RAM used for disk cache (kernel will FREE this when apps need it)
#   available = REAL available memory = free + reclaimable cache ← THIS IS WHAT MATTERS!
# Rule: If "available" is low → you're actually running out of memory
#        If "free" is low but "available" is high → totally normal! Cache is good!

free -h -s 2                               # Repeat memory check every 2 seconds (live monitoring)
cat /proc/meminfo                          # Detailed memory info — everything the kernel knows about RAM
cat /proc/meminfo | grep -i "memavailable\|memfree\|memtotal\|swaptotal"
                                               # Quick check — the 4 most important memory values

# ── VIRTUAL MEMORY STATS ─────────────────────────────────────
vmstat 1 5                                 # Show VM stats every 1 second, 5 times total
# Key columns:
#   r  = Processes waiting for CPU (run queue) — high = CPU bottleneck
#   b  = Processes in uninterruptible sleep (blocked on I/O) — high = disk bottleneck
#   si = Swap in (KB/s)    so = Swap out (KB/s) — ANY swap activity = memory pressure!
#   us = User CPU %  sy = System CPU %  id = Idle %  wa = I/O Wait %
# Rule: if 'wa' is high → disk is the bottleneck, not CPU

# ── CPU & LOAD AVERAGE ───────────────────────────────────────
uptime                                     # Show system uptime + load average
# Output: 14:30:05 up 45 days, load average: 2.15, 1.89, 1.65
#                                            ^^^^  ^^^^  ^^^^
#                                            1min  5min  15min
# Load Average = average number of processes waiting for CPU
#   1-min  = current spike indicator (most recent trend)
#   5-min  = short-term average (are things settling down?)
#   15-min = long-term baseline (overall trend)
# RULE: Load average > number of CPU cores = system is OVERLOADED

nproc                                      # Show number of CPU cores — your load average threshold
lscpu                                      # Detailed CPU info — architecture, cores, threads, cache sizes
lscpu | grep "^CPU(s):"                    # Quick: how many logical CPUs
cat /proc/loadavg                          # Raw load average — same data as uptime, plus running/total processes
# Output: 2.15 1.89 1.65 3/412 28576
#          ^load averages^  ^running/total^  ^last PID created

# ── DISK I/O MONITORING ──────────────────────────────────────
iostat -xz 1                               # Extended I/O stats for all active disks, every 1 second
# Key columns:
#   %util  = Disk utilization — 100% means disk is completely saturated
#   await  = Average I/O wait time (ms) — high = slow disk or overloaded
#   r/s    = Reads per second       w/s  = Writes per second

sar -r 1 3                                 # Memory usage history — sample every 1 sec, 3 times

LVM (Logical Volume Manager) — Concepts

LVM adds a flexible layer between physical disks and filesystems. Instead of fixed partitions, you get resizable volumes that can span multiple disks — essential for production servers.

LAYER 1 — Physical Volume (PV)
Physical disks or partitions initialized for LVM.
Example: /dev/sdb, /dev/sdc1

Think of PVs as raw building blocks — individual bricks you contribute to the pool.
LAYER 2 — Volume Group (VG)
Pool of storage created from one or more PVs.
Example: vg_data (combining sdb + sdc)

Think of VG as a storage pool — merge multiple disks into one large pool.
LAYER 3 — Logical Volume (LV)
Virtual partitions carved from VG. These get formatted and mounted.
Example: /dev/vg_data/lv_app

Think of LVs as flexible partitions — resize anytime without downtime!

1 Initialize disks as PVs → 2 Create a VG from PVs → 3 Create LVs from VG → 4 Format LVs with filesystem → 5 Mount & add to fstab → 6 Extend anytime when you need more space!

LVM Commands — Complete Workflow
LVM Operations 
# ── PHYSICAL VOLUME (PV) — Initialize Disks ─────────────────

sudo pvcreate /dev/sdb                       # initialize /dev/sdb as a physical volume for LVM
sudo pvcreate /dev/sdc /dev/sdd              # initialize multiple disks at once
sudo pvdisplay                                # detailed info about all physical volumes
sudo pvs                                      # short summary — PV name, VG, size, free space
# Output:
#   PV         VG       Fmt  Attr  PSize    PFree
#   /dev/sdb   vg_data  lvm2 a--   100.00g  100.00g
#   /dev/sdc   vg_data  lvm2 a--   100.00g  100.00g


# ── VOLUME GROUP (VG) — Create Storage Pool ──────────────────

sudo vgcreate vg_data /dev/sdb /dev/sdc    # create VG named "vg_data" from two PVs (200G pool)
sudo vgdisplay                                # detailed info about all volume groups
sudo vgdisplay vg_data                       # detailed info for specific VG
sudo vgs                                      # short summary — VG name, PV count, LV count, size, free
# Output:
#   VG       #PV  #LV  #SN  Attr   VSize    VFree
#   vg_data    2    0    0  wz--n- 199.99g  199.99g

sudo vgextend vg_data /dev/sdd              # add another disk to existing VG — expand the pool!
# Now vg_data = sdb + sdc + sdd = 300G total


# ── LOGICAL VOLUME (LV) — Create Virtual Partitions ──────────

sudo lvcreate -L 30G -n lv_app vg_data    # create 30G logical volume named "lv_app" in vg_data
sudo lvcreate -L 50G -n lv_db vg_data     # create 50G logical volume for database
sudo lvcreate -l 100%FREE -n lv_log vg_data # use ALL remaining space in VG

sudo lvdisplay                                # detailed info about all logical volumes
sudo lvs                                      # short summary — LV name, VG, size, status
# Output:
#   LV      VG       Attr       LSize   Origin  Snap%  ...
#   lv_app  vg_data  -wi-a-----  30.00g
#   lv_db   vg_data  -wi-a-----  50.00g


# ── FORMAT & MOUNT LVM VOLUMES ───────────────────────────────

sudo mkfs.ext4 /dev/vg_data/lv_app           # format LV with ext4 filesystem
sudo mkfs.xfs /dev/vg_data/lv_db             # format LV with XFS filesystem

sudo mkdir -p /opt/app                       # create mount point directory
sudo mount /dev/vg_data/lv_app /opt/app     # mount the logical volume

# Add to /etc/fstab for permanent mount:
# /dev/vg_data/lv_app  /opt/app  ext4  defaults  0  2


# ── EXTEND LOGICAL VOLUME (Most Common LVM Task!) ────────────

# Method 1: Extend by specific size
sudo lvextend -L +5G /dev/vg_data/lv_app    # add 5GB to lv_app
sudo resize2fs /dev/vg_data/lv_app           # resize ext4 filesystem to use new space (REQUIRED!)
# OR for XFS:
sudo xfs_growfs /opt/app                     # resize XFS filesystem (uses mount point, not device!)

# Method 2: Extend and auto-resize in ONE command (recommended!)
sudo lvextend -r -L +5G /dev/vg_data/lv_app  # -r flag auto-detects and resizes filesystem!

# Method 3: Use ALL remaining free space in VG
sudo lvextend -r -l +100%FREE /dev/vg_data/lv_app  # extend to use all free VG space + auto-resize FS

# Method 4: Set exact final size
sudo lvextend -r -L 100G /dev/vg_data/lv_app  # set lv_app to exactly 100G total


# ── REDUCE LOGICAL VOLUME (⚠️ DANGEROUS — Backup First!) ────

sudo umount /opt/app                          # must unmount first!
sudo e2fsck -f /dev/vg_data/lv_app           # force filesystem check (required before shrink)
sudo resize2fs /dev/vg_data/lv_app 20G      # shrink filesystem to 20G first
sudo lvreduce -L 20G /dev/vg_data/lv_app    # then shrink LV to 20G
sudo mount /dev/vg_data/lv_app /opt/app     # remount
# ⚠️ XFS does NOT support shrinking! Only ext4 can be reduced.


# ── LVM REMOVAL (Cleanup) ────────────────────────────────────

sudo umount /opt/app                          # unmount first
sudo lvremove /dev/vg_data/lv_app             # remove logical volume (asks for confirmation)
sudo vgremove vg_data                        # remove volume group (all LVs must be removed first)
sudo pvremove /dev/sdb                       # remove PV label from disk
TIP
In production, always use lvextend -r flag to automatically resize the filesystem after extending. Without -r, the LV grows but the filesystem won't see the new space! You'll wonder why df -h still shows the old size — because you forgot to resize the filesystem. The -r flag handles both ext4 (resize2fs) and XFS (xfs_growfs) automatically.
WARNING
Before modifying partitions or LVM, always backup critical data. Wrong fdisk operations can destroy your entire partition table. Never run lvreduce without shrinking the filesystem first — you will lose data. Also: XFS cannot be shrunk, only grown. Always double-check device names (/dev/sda vs /dev/sdb) before any destructive operation!

SSH, Remote Access & Port Forwarding

🔐
SSH Core Concepts & Architecture

SSH (Secure Shell) is a cryptographic network protocol operating on port 22 for secure data communication, remote command execution, and encrypted tunneling. DevOps workflows rely heavily on key-based authentication over password-based logins for automation, CI/CD, and zero-trust bastion architectures.

KEY PAIR CONCEPT
Public Key (.pub): Placed on remote servers in ~/.ssh/authorized_keys. Safe to share.
Private Key (no ext): Kept safe on your client machine. Never shared!
ALGORITHM CHOICE
ED25519 (Recommended): Faster, smaller key size (256-bit), and higher security than RSA.
RSA 4096: Legacy fallback when ancient systems do not support Ed25519.
FILE PERMISSIONS RULE
SSH client strictly fails if key permissions are too open: ~/.ssh → 700 (drwx------)
id_ed25519 → 600 (-rw-------)
authorized_keys → 600 (-rw-------)
SSH Key Management & Setup
# ── KEY GENERATION ──────────────────────────────────────────
ssh-keygen -t ed25519 -C "devops@company.com"    # Generate modern Ed25519 keypair with comment
ssh-keygen -t rsa -b 4096 -C "legacy-server"    # Fallback RSA 4096-bit key
ssh-keygen -p -f ~/.ssh/id_ed25519              # Change or add passphrase to existing private key

# ── COPY PUBLIC KEY TO REMOTE SERVER ────────────────────────
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@192.168.1.50   # Auto-installs public key into remote authorized_keys
ssh-copy-id -p 2222 user@192.168.1.50                    # Specify custom SSH port during key copy
# Manual fallback without ssh-copy-id:
cat ~/.ssh/id_ed25519.pub | ssh user@server "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"

# ── CRITICAL SSH PERMISSIONS (STRICT CHECK) ─────────────────
chmod 700 ~/.ssh                                # Owner read/write/execute only
chmod 600 ~/.ssh/id_ed25519                     # Private key: strictly owner read/write only
chmod 644 ~/.ssh/id_ed25519.pub                 # Public key: world-readable
chmod 600 ~/.ssh/authorized_keys                # Authorized keys file
chmod 644 ~/.ssh/known_hosts                    # Known host fingerprints

# ── SSH AGENT (REMEMBER PASSPHRASES IN MEMORY) ──────────────
eval "$(ssh-agent -s)"                         # Start SSH agent daemon in current shell
ssh-add ~/.ssh/id_ed25519                       # Cache private key passphrase for this session
ssh-add -l                                      # List all currently cached keys
ssh-add -D                                      # Delete / flush all cached keys from memory

# Remote Forwarding (-R): Expose your local dev server to remote users
ssh -R 8080:localhost:3000 user@remote-vps      # Remote users hit vps:8080 → hits your local 3000
# Dynamic SOCKS Proxy (-D): Route browser traffic through remote host
ssh -D 1080 -N -f user@bastion                  # Background SOCKS5 proxy on local port 1080

# ── SECURE FILE TRANSFER (SCP & RSYNC) ──────────────────────
scp build.tar.gz user@server:/opt/app/            # Copy file from local to remote server
scp -r ./dist/ user@server:/var/www/html/         # Recursively copy directory to remote
rsync -avz --progress ./src/ user@server:/opt/app/ # Fast delta-sync with compression & progress bar
rsync -avz -e "ssh -p 2222" ./ user@server:/opt/ # Rsync over custom SSH port
SECURITY WARNING — PRODUCTION SSH HARDENING
In /etc/ssh/sshd_config, always set: PasswordAuthentication no (disallow password brute-forcing), PermitRootLogin prohibit-password (or no), and MaxAuthTries 3. Always reload via systemctl reload sshd while keeping an existing SSH session open to verify you are not locked out!

Production Bash Scripting Best Practices

📝
The Golden Rule: Strict Mode (`set -euo pipefail`)

By default, Bash happily continues executing even when commands fail or variables are misspelled. In production automation or CI/CD pipelines, this silent behavior causes catastrophic data loss (e.g. running rm -rf $DIR/ when $DIR is empty deletes root /!). Always place strict mode at the top of every script.

Flag Full Option Name DevOps Production Benefit
-e set -o errexit Immediately exits script if any command returns a non-zero exit code (error).
-u set -o nounset Treats unset/uninitialized variables as an error and exits immediately (prevents empty variable deletion bugs).
-o pipefail set -o pipefail If ANY command in a pipeline fails (e.g. cmd1 | cmd2), the entire pipeline fails, not just the last command.
-x set -o xtrace Prints each command before executing it. Use during debugging or CI/CD runs.
Production Bash Script Template with Error Trapping
#!/usr/bin/env bash
# ==============================================================================
# Production Automated Backup & Health Report Script
# ==============================================================================
set -euo pipefail
IFS=$'\n\t'                                     # Strict word splitting (newlines and tabs only)

# ── CONSTANTS & DIRECTORIES ─────────────────────────────────
readonly SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
readonly BACKUP_ROOT="/var/backups/app"
readonly LOG_FILE="/var/log/backup-$(date +%Y%m%d).log"
readonly TIMESTAMP="$(date +'%Y-%m-%d_%H-%M-%S')"

# ── ERROR HANDLING & CLEANUP TRAP ───────────────────────────
cleanup() {
    local exit_code=$?
    if [ $exit_code -ne 0 ]; then
        echo "[ERROR] Script failed on line ${BASH_LINENO[0]} (exit code: $exit_code)" >> "$LOG_FILE"
    fi
    rm -rf /tmp/backup_temp_$$                   # Clean up temporary scratch files
}
trap cleanup EXIT INT TERM ERR                   # Always triggers cleanup on exit or error!

# ── LOGGING HELPER ──────────────────────────────────────────
log() {
    echo "[$(date +'%Y-%m-%dT%H:%M:%S%z')] $*" | tee -a "$LOG_FILE"
}

# ── MAIN EXECUTION ──────────────────────────────────────────
main() {
    log "Starting automated database backup for: $TIMESTAMP"
    
    if [ "$(id -u)" -ne 0 ]; then
        echo "Fatal: This script must be executed as root" >&2
        exit 1
    fi

    mkdir -p "$BACKUP_ROOT"
    mkdir -p /tmp/backup_temp_$$

    log "Archiving application assets..."
    tar -czf "$BACKUP_ROOT/assets-$TIMESTAMP.tar.gz" /var/www/uploads/

    # Retention policy: Delete backups older than 14 days
    log "Purging backups older than 14 days..."
    find "$BACKUP_ROOT" -type f -name "*.tar.gz" -mtime +14 -delete

    log "Backup completed successfully!"
}

main "$@"

Production Emergency Commands 
# ── SERVER SLOW? ─────────────────────────────────────
uptime                                        # check load averages — if > CPU cores, server is overloaded
top -bn1 | head -20                          # snapshot of top processes — find the CPU/memory hog
